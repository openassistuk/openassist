# OpenAssist v0.2.0 stable

This is the first stable packaged release for Linux glibc and macOS, each on x64 and arm64. Packages include OpenAssist, production dependencies and a private Node 24.21.0 runtime. Git, pnpm and system Node are not required for packaged installation.

The commands below require the signed `v0.2.0` assets on the repository's Releases page. Before stable publication, select the published [v0.2.0-rc.1 preview](v0.2.0-rc.1.md) with `--channel preview`. Publication status, candidate verification and remaining checks are recorded in the [stable preparation plan](../execplans/stable-0.2.0-release.md).

## Changes since the preview

- Fix piped installer terminal input, fresh-install setup selection and packaged setup without Git/npm/pnpm. Correct macOS Bash 3 handoff and nested packaged trust-anchor discovery.
- Verify setup activation against both build and instance identity, report pending recovery accurately, refresh timezone health after confirmation and give systemd/launchd the managed command and Node paths.
- Correct recurring `skip` scheduling so on-time work executes while missed slots advance without dispatch.
- Add durable one-shot text reminders and tool-free scheduled prompts through chat tools, CLI and daemon APIs. Chat access requires an approved Full access operator and stays within the current chat. Original request deadlines, deduplication, results and delivery receipts survive restart. Successful sends are not repeated; ambiguous sends are not retried automatically. Cancellation suppresses remaining parts without claiming to retract an in-flight send.
- Resolve the Undici WebSocket-handshake and brace-expansion denial-of-service advisories with scoped Undici `6.28.1` and brace-expansion `5.0.12` resolutions. Production and full dependency audits remain mandatory. The previously published preview assets are unchanged.
- Correct CodeQL account-link fixture classification using fixed non-secret temporary directory prefixes. Runtime instance fingerprints remain path-only SHA-256 values with existing identity and authentication boundaries preserved.
- Add verification of immutable published assets and bounded public-download diagnostics. Signature failures remain blocking; download errors never select unsigned assets or silently fall back to source.

## Included in the stable release

The full [0.2.0 changelog](../../CHANGELOG.md) records the development line since 0.1.0. It includes signed packaged installation, staged updates, retained application rollback, durable recovery, isolated developer instances and ownership-checked uninstall with state preservation by default. Operator state lives outside the application under the normal config/data/log/skill directories.

The assistant supports five provider routes: OpenAI API key, Codex account login, Anthropic, Azure Foundry and OpenAI-compatible. Guided setup, catalog-based model controls, bounded provider reasoning replay, rolling session summaries, actor-scoped memory, channel attachments and targeted file delivery retain their configured access boundaries. Telegram, Discord and WhatsApp MD remain the built-in channels. See the [configuration reference](../configuration/config-reference.md) and [provider/channel readiness](../operations/provider-channel-readiness.md) for supported controls and testing limits.

## Fresh installation after publication

Run on a supported Linux or macOS host:

```bash
curl -fsSL https://raw.githubusercontent.com/openassistuk/openassist/main/install.sh | bash
```

To select this exact version, use:

```bash
curl -fsSL https://raw.githubusercontent.com/openassistuk/openassist/main/install.sh | bash -s -- --version 0.2.0
```

The installer verifies signatures and hashes before executing downloaded application code, then opens guided setup on an interactive terminal. Open a new terminal for the saved PATH block, or use `~/.local/bin/openassist setup`. Finish with `openassist doctor` and `openassist service health`. See the [quickstart](../operations/quickstart-linux-macos.md) and [common troubleshooting](../operations/common-troubleshooting.md).

## Existing preview and source installations

Back up configuration, credentials and the database before upgrading. Use the installed updater rather than rerunning fresh bootstrap:

```bash
openassist update --release --channel stable --dry-run
openassist update --release --channel stable
openassist doctor
openassist service health
```

The explicit stable selection changes a preview, exact-version or source track to stable. Source installations otherwise retain their recorded source track; exact-version installs remain pinned. Older source clients must first update their CLI using the supported source path. Source development requires Node `>=24.21.0 <25` and pnpm `12.5.1`; packaged clients use their private runtime.

Managed updates retain operator configuration, credentials, conversations and memory, and keep the previous application/runtime for compatible rollback. One-shot SQLite tables are additive at database compatibility version 1. Rollback to rc.1 or another build without `managed-one-shots-v1` is blocked while reminders are nonterminal. Complete or cancel tasks and let in-flight work settle before rollback; do not delete state to bypass the guard. Application rollback never silently restores an older database. See [upgrade and rollback](../operations/upgrade-and-rollback.md).

## Platform and verification limits

Linux requires glibc 2.28+ and kernel 4.18+; macOS requires 13.5+. Alpine/musl and Windows operator installation are unsupported. Windows remains a quality/coverage platform. Full access is OpenAssist's highest tool profile and does not grant Unix root; Linux systemd filesystem policy remains a separate service boundary.

The release gates cover Linux/macOS x64/arm64 artifacts, private-runtime onboarding, the signed rc.1 updater transition, retained operator state, Linux service activation, macOS LaunchAgent behavior and ephemeral signing-contract checks. Hosted checks must pass for this candidate. Previous preview public-install checks and the destroyed Ubuntu host are baseline evidence only. Replacement-host candidate testing and the skipped live second-account check remain unverified. Post-publication stable-channel and exact-version public installs are still required on all four targets.

Report the release version, OS/architecture, installation method and sanitized reproduction steps when filing an issue. Keep credentials, private conversations and signing material out of reports.
